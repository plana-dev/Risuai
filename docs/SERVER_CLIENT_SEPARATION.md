# 서버-클라이언트 기능 분리 원칙

**작성일**: 2026년 1월  
**기준**: 서버 모듈(`src/server`)과 클라이언트(`src/ts`) 간 기능 분리 가이드라인

---

## 📋 개요

이 문서는 RisuAI 서버화 작업에서 **서버와 클라이언트 간 기능 분리 원칙**을 정의합니다. 서버는 **상태 변경과 비즈니스 로직의 권위(Authoritative)**를 가지며, 클라이언트는 **표시와 연출(View/Actor)**을 담당합니다.

---

## 🎯 분리 원칙

### 서버에서 처리하는 기능 (서버 권위 - Authoritative)

서버는 **상태 변경과 비즈니스 로직의 단일 진실 공급원(Single Source of Truth)**입니다.

#### 1. 상태 변경
- **변수 관리**: 채팅 변수, 전역 변수, 캐릭터 변수
- **인벤토리**: 게임 내 아이템, 상태 관리
- **퀘스트/플래그**: 진행 상태, 분기 플래그
- **데이터베이스 쓰기**: 모든 영속성 있는 상태 변경

#### 2. 과금 확정
- **토큰 사용량 계산**: 정확한 토큰 수 계산 및 기록
- **크레딧 차감**: API 호출 비용 계산 및 차감
- **정산**: 사용량 집계 및 청구

#### 3. 스크립트 실행 (상태 변경 포함)
- **editinput**: 사용자 입력 처리 전 (상태 변경 가능)
- **editprocess**: 처리 중 (상태 변경 가능)
- **editoutput**: AI 출력 처리 후 (상태 변경 가능)
- **editdisplay**: ❌ 서버에서 처리하지 않음 (클라이언트 전용)

#### 4. 트리거 실행 (상태 변경 포함)
- **input**: 입력 트리거 (상태 변경 가능)
- **output**: 출력 트리거 (상태 변경 가능)
- **request**: 요청 전 트리거 (상태 변경 가능)
- **start**: 시작 트리거 (상태 변경 가능)
- **display**: ❌ 서버에서 처리하지 않음 (클라이언트 전용)

#### 5. 프롬프트 구성
- **최종 프롬프트 조립**: 모든 템플릿, 메모리, 로어북 통합
- **LLM 호출**: API 요청 및 응답 처리
- **토큰 계산**: 정확한 토큰 수 계산

#### 6. 메모리 처리
- **SupaMemory**: 메모리 요약 및 관리
- **HypaMemory V2/V3**: 하이퍼메모리 처리
- **HanuraiMemory**: 한우라이 메모리 처리
- **임베딩 생성**: 벡터 임베딩 생성 (서버 사이드)

#### 7. 영속성 관리
- **세션 저장**: 채팅 상태 저장
- **메시지 히스토리 관리**: 메시지 저장 및 로드
- **데이터베이스 동기화**: 상태 일관성 보장

### 클라이언트에서 처리하는 기능 (클라이언트 연출 - View/Actor)

클라이언트는 **표시와 사용자 경험(UX)**을 담당하며, **상태 변경을 직접 수행하지 않습니다**.

#### 1. 입력 수집
- **사용자 입력**: 텍스트 입력, 파일 업로드
- **Optimistic UI**: 즉시 반응하는 UI 업데이트 (서버 확인 전)

#### 2. 스트리밍 표시
- **SSE/WebSocket 수신**: 서버로부터 실시간 데이터 수신
- **점진적 렌더링**: 스트리밍 텍스트를 실시간으로 표시
- **Visual-only**: 표시만 담당, 상태 변경 없음

#### 3. 연출 처리 (Visual-only)
- **에셋 매크로**: `{{asset::id}}` → 이미지 표시
- **마크다운 렌더링**: 텍스트를 HTML로 변환하여 표시
- **CBS 파싱 (표시용)**: 화면에 표시하기 위한 파싱
- **상태 변경 금지**: 모든 연출은 읽기 전용

#### 4. editdisplay 스크립트
- **표시 전 처리**: 화면에 표시하기 전 텍스트 변환
- **Visual-only**: 상태 변경 금지
- **예시**: 마크다운 변환, 이모지 변환, 텍스트 필터링

#### 5. display 트리거
- **표시 전 Lua 스크립트**: 화면 표시 전 실행
- **Visual-only**: 상태 변경 금지
- **UI 업데이트만**: 표시 관련 변경만 허용

#### 6. UI 반영
- **state_patch 수신**: 서버로부터 상태 변경 패치 수신
- **system_events 처리**: 서버 이벤트를 UI에 반영
- **로컬 상태 동기화**: 서버 상태와 클라이언트 UI 동기화

#### 7. TTS 처리
- **브라우저 API 사용**: Web Speech API, Audio API
- **오디오 재생**: 서버가 생성한 오디오 데이터 재생
- **로컬 TTS**: 클라이언트 사이드 TTS 엔진 사용

#### 8. 이모션 이미지
- **UI 상태 업데이트**: 감정 이미지 표시
- **로컬 상태 관리**: 화면 표시용 상태만 관리

#### 9. 이미지 생성 (UI 연출용)
- **Stable Diffusion**: 이미지 생성 (연출용)
- **Inlay 처리**: 이미지 삽입 처리
- **멀티모달 변환**: 클라이언트에서 멀티모달 데이터 처리

#### 10. 사운드/비디오 재생
- **미디어 재생**: 오디오/비디오 파일 재생
- **로컬 처리**: 브라우저 API 사용

### 클라이언트 금지 사항

클라이언트는 다음을 **절대 수행하지 않아야** 합니다:

- ❌ **서버 상태 변경 로직 실행 금지**
  - 변수 변경, 인벤토리 수정, 플래그 변경 등
  - 모든 상태 변경은 서버를 통해야 함

- ❌ **서버 전용 커맨드/태그 해석 금지**
  - 서버만 처리하는 태그를 클라이언트에서 해석하여 상태 변경 금지
  - 예: `{{setVar::key::value}}` 같은 상태 변경 태그

- ❌ **프롬프트 최종 조립 금지**
  - 프롬프트 템플릿, 메모리, 로어북 통합은 서버만 수행
  - 클라이언트는 표시용 파싱만 수행

- ❌ **editinput, editoutput 스크립트 실행 금지**
  - 상태 변경이 포함될 수 있는 스크립트는 서버만 실행
  - 클라이언트는 editdisplay만 실행

- ❌ **input, output 트리거 실행 금지**
  - 상태 변경이 포함될 수 있는 트리거는 서버만 실행
  - 클라이언트는 display 트리거만 실행

## 🔍 미구현 항목 분석 (MISSING_FEATURES.md 기준)

### 서버 모듈에서 사용하지 않음 (클라이언트 전용)

다음 항목들은 원본에는 존재하지만, 서버 모듈에서는 사용하지 않기로 결정했습니다:

#### 1. 플러그인 시스템
- **위치**: `src/ts/plugins/*`
- **사유**: 
  - 서버 보안상 사용자 코드 실행은 위험
  - 서비스 웹 특성상 클라이언트에서만 필요
- **영향**: 
  - 플러그인 훅(beforeRequest/afterRequest, edit 핸들러 등)은 서버에서 지원하지 않음
  - 커스텀 Provider, 커스텀 토크나이저도 플러그인 없이 직접 구현 필요 시 별도 처리

#### 2. MCP 시스템
- **위치**: `src/ts/process/mcp/*`
- **사유**: 서버 모듈에서 사용하지 않음

#### 3. WebLLM
- **위치**: `src/ts/process/webllm.ts`
- **사유**: 브라우저 로컬 LLM (클라이언트 전용)

#### 4. Python Worker (Pyodide)
- **위치**: `src/ts/process/pyworker.ts`
- **사유**: 브라우저 워커 (클라이언트 전용)

#### 5. ZIP/CharX 처리
- **위치**: `src/ts/process/processzip.ts`
- **사유**: 클라이언트 전용 (파일 업로드/다운로드)

#### 6. PDF 처리
- **위치**: `src/ts/process/dynamicutils/pdf.ts`
- **사유**: Canvas 기반 렌더링 (클라이언트 전용)

#### 7. MultiSend
- **위치**: `src/ts/process/files/multisend.ts`
- **사유**: 클라이언트 파일 첨부 UX

#### 8. 드라이브/백업
- **위치**: `src/ts/drive/*`
- **사유**: 클라이언트 백업/동기화

## 🎨 Inlay 처리 및 멀티모달/이미지 임베딩

### 결정: 서버에서 멀티모달/이미지 임베딩 지원하지 않음

**Inlay 처리**는 서버에서 기본 구조만 제공하고, **멀티모달 변환 및 이미지 임베딩**은 서버에서 처리하지 않습니다.

#### 서버에서 처리하는 Inlay 기능

- ✅ **Inlay 에셋 저장**: `writeInlayImage()` - Redis에 저장
- ✅ **Inlay 에셋 조회**: `getInlayAsset()` - Redis에서 조회
- ✅ **Inlay Screen 처리**: `runInlayScreen()` - 태그 변환 (Emotion, ImgGen)

#### 서버에서 처리하지 않는 Inlay 기능

- ❌ **멀티모달 변환**: Inlay 에셋을 `multimodals` 배열로 변환
- ❌ **이미지 임베딩**: 이미지를 텍스트 캡션으로 변환
- ❌ **멀티모달 전송**: LLM API에 멀티모달 데이터 전송

#### 클라이언트에서 처리하는 Inlay 기능

클라이언트는 다음을 처리합니다:

1. **멀티모달 변환**
   - Inlay 태그(`{{inlayeddata::id}}`) 추출
   - Inlay 에셋 조회
   - 모델 지원 여부 확인
   - 멀티모달 배열 구성 또는 이미지 임베딩 사용

2. **이미지 임베딩 (선택적)**
   - 모델이 이미지 입력을 지원하지 않는 경우
   - 클라이언트에서 이미지 임베딩 실행
   - 또는 사용자가 선택하여 사용

3. **멀티모달 전송**
   - 클라이언트에서 멀티모달 데이터를 서버로 전송
   - 서버는 받은 멀티모달 데이터를 그대로 LLM에 전달

#### 사용자 선택 기능

다음 기능들은 **사용자가 선택하여 사용**할 수 있도록 클라이언트에서 처리:

- **이미지 생성**: Stable Diffusion 등 (UI 연출용)
- **사운드**: 오디오 파일 재생
- **TTS**: 텍스트-음성 변환 (브라우저 API)
- **이모션 출력**: 감정 이미지 표시

## 🔄 데이터 흐름

### 일반적인 채팅 흐름

```
1. 클라이언트: 사용자 입력 수집
   ↓
2. 클라이언트 → 서버: 입력 데이터 전송 (multimodals 포함 가능)
   ↓
3. 서버: editinput 스크립트 실행 (상태 변경 가능)
   ↓
4. 서버: input 트리거 실행 (상태 변경 가능)
   ↓
5. 서버: 프롬프트 조립 (템플릿, 메모리, 로어북 통합)
   ↓
6. 서버: LLM 호출 (multimodals 포함하여 전송)
   ↓
7. 서버: 응답 수신
   ↓
8. 서버: editoutput 스크립트 실행 (상태 변경 가능)
   ↓
9. 서버: output 트리거 실행 (상태 변경 가능)
   ↓
10. 서버: 상태 저장 (DB 업데이트)
   ↓
11. 서버 → 클라이언트: 응답 데이터 전송 (스트리밍 또는 일괄)
   ↓
12. 클라이언트: editdisplay 스크립트 실행 (visual-only)
   ↓
13. 클라이언트: display 트리거 실행 (visual-only)
   ↓
14. 클라이언트: 연출 처리 (마크다운, 에셋 등)
   ↓
15. 클라이언트: 화면 표시
```

### 멀티모달 처리 흐름 (서비스웹에서는 멀티모달을 사용하지 않도록 클라이언트에서 제공하지 않음)

```
1. 클라이언트: 사용자가 이미지 업로드
   ↓
2. 클라이언트: 이미지를 Inlay 에셋으로 저장 요청
   ↓
3. 서버: Inlay 에셋 저장 (Redis)
   ↓
4. 서버 → 클라이언트: Inlay ID 반환
   ↓
5. 클라이언트: 멀티모달 변환
   - 모델 지원 여부 확인
   - 지원: multimodals 배열 구성
   - 미지원: 이미지 임베딩 실행 (선택적)
   ↓
6. 클라이언트 → 서버: 입력 데이터 + multimodals 전송
   ↓
7. 서버: LLM 호출 (multimodals 포함하여 전송)
   ↓
8. 서버 → 클라이언트: 응답 전송
   ↓
9. 클라이언트: 멀티모달 응답 표시
```

## 🚫 서버에서 제외된 기능 상세

### 1. 플러그인 시스템

**제외 사유:**
- 보안 위험 (사용자 코드 실행)
- 서비스 웹 특성상 클라이언트에서만 필요
- 서버 코드 단순화

**영향:**
- 플러그인 훅(beforeRequest/afterRequest) 미지원
- edit 핸들러 플러그인 미지원
- 커스텀 Provider 플러그인 미지원
- 커스텀 토크나이저 플러그인 미지원

**대안:**
- 커스텀 Provider가 필요하면 서버 코드에 직접 구현
- 커스텀 토크나이저가 필요하면 서버 코드에 직접 구현

### 2. Inlay 멀티모달/이미지 임베딩

**제외 사유:**
- 멀티모달 변환은 클라이언트에서 처리하는 것이 적합
- 이미지 임베딩은 선택적 기능 (사용자가 선택)
- 서버 부하 감소

**서버 역할:**
- Inlay 에셋 저장/조회만 담당
- 클라이언트가 구성한 multimodals를 그대로 LLM에 전달

**클라이언트 역할:**
- Inlay 태그 추출 및 멀티모달 변환
- 이미지 임베딩 실행 (선택적)
- 멀티모달 데이터 구성

### 3. TTS, 이미지 생성, 이모션

**제외 사유:**
- UI 연출용 기능
- 브라우저 API 의존
- 사용자 선택 기능

**처리 방식:**
- 클라이언트에서 처리
- 서버는 필요 시 오디오 데이터만 생성하여 전송
- 실제 재생/표시는 클라이언트에서 수행

## 📝 구현 가이드라인

### 서버 구현 시

1. **상태 변경은 항상 서버에서**
   - 변수 변경, DB 쓰기는 서버만 수행
   - 클라이언트는 읽기만 가능

2. **프롬프트 조립은 서버에서**
   - 모든 템플릿, 메모리 통합은 서버에서
   - 클라이언트는 최종 프롬프트를 받아서 표시만

3. **멀티모달은 클라이언트에서 구성**
   - 서버는 받은 multimodals를 그대로 전달
   - 멀티모달 변환 로직은 클라이언트에

4. **스트리밍은 서버 → 클라이언트**
   - 서버가 스트리밍 데이터 전송
   - 클라이언트가 실시간 표시

### 클라이언트 구현 시

1. **상태 변경 금지**
   - 모든 상태 변경은 서버 API 호출
   - 로컬 상태는 표시용으로만 사용

2. **editdisplay만 실행**
   - editinput/output/process는 서버에서만
   - display 트리거만 클라이언트에서 실행

3. **멀티모달 변환 담당**
   - Inlay 태그 추출 및 변환
   - 이미지 임베딩 실행 (선택적)
   - multimodals 배열 구성

4. **연출 처리만 수행**
   - 마크다운 렌더링
   - 에셋 표시
   - 상태 변경 없이 표시만
